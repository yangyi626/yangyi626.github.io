项目背景

AIPC Agent 和普通聊天机器人不同，它需要长期执行真实任务：读写文件、调用终端、操作浏览器、管理 NAS、处理权限审批，并在多轮任务中保持状态一致。核心难点包括长链路规划、上下文污染、工具误用、多 Agent 协同、执行安全和结果可评测性。

关键问题：如果只靠 prompt，很难稳定解决 Agent 在真实任务中的失败。需要把运行过程结构化为 trace，把失败归因到模型、工具、上下文、workflow、verifier 或环境，再决定是修框架、修数据，还是进入后训练。

Agent 框架设计

我参与的框架设计围绕“任务输入 → 意图理解 → 计划生成 → 多 Agent 协同 → 工具调用 → 结果校验 → Trace 记录 → 状态更新”展开。

模块职责
Planner Agent理解任务目标，拆解步骤，决定是否需要工具、记忆或子任务协同。
Executor Agent执行文件、终端、浏览器、NAS 等工具调用，并把环境反馈写入轨迹。
Verifier / Critic检查结果是否满足任务 contract，识别格式、逻辑或执行失败。
Tool Layer统一工具 schema、异常处理、超时控制、权限边界和日志格式。
Trace Pipeline记录 messages、tool calls、observations、scores、失败类型和中间状态。

在落地时，我把框架拆成可版本化的 Harness 组件，而不是把 prompt、工具和评测逻辑写死在一次运行中。组件包括 model caller、prompts、context、memory、skills、tools、workflows、validators、sandbox、runtime 和 trace，每个 HarnessVersion 绑定一组 ComponentVersion，便于灰度对比、失败回滚和针对任务族做局部优化。

运行时实现

Runtime binding 负责把注册表中的 HarnessVersion 解析成一次任务可见的运行时快照。该层会汇总组件 profile、prompt overrides、context hints、tool policy、workflow policy、validator policy、sandbox policy 和 trace policy。

组件解析 从组件注册表读取版本信息，加载对应组件产物，把 artifact payload 和 semantic patch 合并成 runtime-visible policy。
Prompt 注入 对 context、memory、skills 三类组件提取 prompt hints，只把当前 Harness 声明的能力注入模型上下文，避免无关能力污染任务。
运行参数收敛 对 validators、sandbox、retry 等组件声明的 CLI 参数做白名单过滤，只允许安全的 runtime flags，例如 max turns、sandbox、shell allow-list 和 no-stream。
Trace 元数据 每次运行会记录 runtime profile、evaluator / parser / trace / sandbox / tool / validator / workflow policy，后续可以按组件维度归因失败。

Memory 管理

Memory 用来解决长任务和多轮任务中的“状态丢失”问题。它不是把所有历史消息塞进上下文，而是按任务、用户和状态类型做结构化写入与召回。

用户偏好记忆

记录用户常用格式、审批习惯、输出偏好和长期约束。

任务事实记忆

记录当前任务目标、已完成步骤、关键文件、工具反馈和中间结果。

项目状态记忆

维护项目路径、环境依赖、历史实验状态和未完成事项。

失败经验记忆

沉淀工具失败、verifier 错误、环境异常和修复经验，用于后续任务规避。

设计重点包括写入策略、召回策略、冲突处理、过期机制和敏感信息边界，避免上下文污染和错误记忆放大。在 HARE-X 实现中，Memory 作为独立组件进入版本注册表。这种设计让记忆策略可以单独升级、回滚和评测，而不需要同时改动工具层或 prompt 层。

Skill 管理

Skill 是可复用能力单元，不只是 prompt。一个 Skill 通常包含触发条件、参数 schema、工具依赖、执行 workflow、约束规则、参考资源和产物格式。

设计点说明
按需加载根据任务类型选择相关 Skill，避免把所有能力塞进上下文。
工具依赖显式声明文件、终端、浏览器、NAS 等工具需求。
权限边界对高风险操作设置审批、沙箱或只读限制。
版本管理保留 Skill 修改历史，便于回滚和评测对比。
失败沉淀从成功经验和失败修复中生成新的 Skill 或更新旧 Skill。

Skill 组件也进入同一套版本系统。面试里可以把它解释成“能力包管理”：模型不直接记住所有操作细节，而是在任务触发时加载相应 skill，skill 再声明工具依赖、输入输出 schema、失败处理方式和验证条件。

Context 管理

Context 管理负责在有限窗口内保留对当前任务最有价值的信息。核心不是“越多越好”，而是让模型在每一步看到正确的任务状态、工具反馈和约束。

  • 长任务上下文压缩：压缩历史消息，保留目标、已完成步骤、失败原因和关键证据。
  • 状态恢复：在任务中断或重试后恢复当前状态，减少重复执行。
  • Memory / RAG 注入：根据任务动态召回用户偏好、项目事实和相关文档。
  • 上下文去噪：裁剪无关工具输出、重复日志和过长 stdout，降低模型注意力干扰。
  • 任务 contract 保留：将输出格式、工具限制和 verifier 条件放在高优先级上下文中。

具体实现上，Context 不是纯文本拼接，而是以组件 policy 的方式进入 runtime，runtime 再抽取可注入提示。这样可以把“长期记忆”“当前任务状态”“工具反馈摘要”“任务 contract”分层管理。

任务 Contract

为了让 Agent 失败可诊断、可训练，我参与了 task contract 抽取与修复链路。

能力实现细节
输出路径抽取从任务描述、测试日志和 shell 命令中抽取 required output file / directory，避免 Agent 只写解释不落盘。
服务与端口识别识别 HTTP URL、端口、service hints 和 subprocess 路径，帮助 Agent 判断是否需要启动服务或检查进程。
断言和指标解析从 pytest assertion、CSV 行列约束、expected numbers、semantic metrics 中提取 verifier 条件。
失败修复工具实现 substitution contract helper：在沙箱内多轮尝试同义替换，运行编译/验证命令，选择能减少 failure signal 的候选。

工程价值：task contract 把自然语言任务转成可执行约束，Trace 再把每一步工具调用和验证结果记录下来。这样后训练数据不只是“最终成功/失败”，而是能定位到哪类组件和哪类动作导致失败。

评测与学习闭环

在框架设计之外，我还参与了 Agent-One 的评测与学习闭环建设：使用 Terminal-Bench 作为真实可执行任务环境，用 vLLM 接入 Qwen 系列本地模型，并把运行过程转为训练数据。

环节内容
Model ServingQwen3.5-4B / 9B + vLLM OpenAI-compatible 接口，处理 tool parser 和上下文长度。
Benchmark接入 Terminal-Bench 2.0，支持 Easy / Medium / Hard 共 89 道任务。
Trace记录 messages、tool traces、actions、observations、tokens、masks、verifier feedback。
Attribution区分模型策略错误、工具协议错误、环境依赖错误、verifier 错误和上下文错误。
Reward / Filter根据任务通过率、动作合法性、工具有效性、步骤冗余和失败类型构造训练信号。

Terminal-Bench 适配层负责把 Harbor job 转换成 HARE-X 的 Trace、EvalRun、TaskResult 和 EvidencePack；批量运行层负责选择任务、并发执行、断点续跑、Docker 拉取失败识别和 pass@1 汇总。

Trace schema 中显式区分模型调用、工具调用、工具结果、状态更新、校验决策、沙箱事件、重试、修复、最终响应和错误事件。这些事件类型使得失败归因可以从自然语言复盘转为结构化统计。

结果口径：Qwen3.5-4B 在 Terminal-Bench Easy 4 题单次 full run 达到 3/4。历史累计进度用于失败归因和训练数据分析，不作为严格同口径排行榜 pass@1。
